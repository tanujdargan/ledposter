# Deviations

Places where the build differs from `docs/spec.md` or `docs/ARCHITECTURE.md`, and why.

## M2: animated WebP on Raspberry Pi OS Bookworm

Spec: the media pipeline accepts WebP. Bookworm ships ffmpeg 5.1, whose WebP decoder handles still images only (it skips the `ANIM`/`ANMF` chunks). Still WebP works everywhere. Animated WebP works with newer ffmpeg builds (verified with 9.0 on macOS), but on the Pi the transcoder rejects it with "Animated WebP is not supported by this system's ffmpeg; convert it to GIF or MP4" plus the supported-format list.

Fix options, if needed: decode animated WebP with Pillow (`python3-pil`) as a fallback, or install a newer ffmpeg build. Neither was done in M2, to keep the dependencies at ffmpeg plus numpy.

## M4: config comments are not preserved

Architecture: one versioned YAML config, written atomically by the web app. The web app rewrites `config.yaml` with PyYAML `safe_dump`, which drops the comments found in `config/config.example.yaml`. Keys, values and `version` are preserved and the file is written atomically with mode 600. Comments live in the example config and the README instead; a comment-preserving library (ruamel.yaml) was not added to keep dependencies short.

## M4: `websockets` added to the web app's dependencies

The M4 plan listed fastapi, uvicorn, python-multipart and pyyaml as the new dependencies. Plain `uvicorn` cannot serve WebSockets (it logs "No supported WebSocket library detected" and answers 404), so `websockets` is required for the preview relay at `/api/preview`. Pure Python, also packaged as `python3-websockets` on Bookworm.

## M4: per-item speed is applied to the cached frame timings

Spec: per-item settings include speed. The transcoder has no speed option and the engine belongs to M3, so the web app applies speed itself: after a transcode it divides every `durations_ms` entry in `meta.json` by `speed` (minimum 1 ms) and records `speed` in the file. The engine plays the adjusted timings unchanged, so no engine support is pending; it only means `durations_ms` in the cache is the playback timing rather than the source timing.

## M4: the preview renderer approximates the transcoder

Spec: uploads show a preview through the dot renderer with the chosen scaling mode and crop applied before they are sent to the wall. Until an item is transcoded (or while its settings are being changed), the browser emulates fit/fill/stretch, crop, position and the pixel/smooth filter with canvas `drawImage` (bilinear, not area averaging; no gamma or dither). Once the cache matches the settings the editor shows real cached frames from `GET /api/media/{id}/frames`, which is exact.

## M6: static IP rollback uses a static systemd timer, not `systemd-run`

Spec: automatic rollback to DHCP if the wall is unreachable 2 minutes after a static IP is applied. The plan suggested `systemd-run --on-active=120`. That needs `org.freedesktop.systemd1.manage-units` for *transient* units, which lets the caller run any command as root under a chosen unit name, so granting it to the `ledwall` service user would be a root path in disguise. Instead `system/systemd/ledposter-net-rollback.timer` (OnActiveSec=120) and `.service` are fixed units installed by M8; the web app only `systemctl restart`s the timer before applying and `stop`s it on confirm. The polkit rule (`system/polkit/49-ledposter-network.rules`) allows exactly those verbs on exactly those units, so no sudoers drop-in is needed. The connection to revert is written to `$LEDPOSTER_DATA/net-rollback` by the web app; `system/bin/ledposter-net rollback` (root, run by the service) reads it and is a no-op when the file was removed by a confirm. Same guarantee as the plan: the revert does not depend on the web app being alive.

The same pattern updates `/etc/hosts` after a hostname change (`hostnamectl` does not touch it): `ledposter-hosts.service` runs `ledposter-net hosts` as root. An alternative is to install `libnss-myhostname` and skip the file; M8 can pick either.

## M6: the IP is shown on the wall at boot, from Settings, and on a button double press (done in M7)

Spec: show the current IP on the wall for 10s at boot and on a button press. Boot: the web app sends `show_text` once the engine is reachable and the network is up (the web app starts at boot, so this is "at boot" plus every web app restart). Settings has "Show address on the wall". The button's short (next mode), long (power) and very long (10s, Wi-Fi setup) presses are all taken by the spec, so the choice is: **a double press shows the hostname and IP** for `network.show_ip_s` (10s). Done in M7: the engine classifies double presses (`button.double_ms`, default 350ms) and counts them in status as `button_double_count`; the web app's setup loop (`wifisetup.py`) sends `show_text` on each new one (the hotspot instructions instead while setup runs). The cost: a short press acts `double_ms` later, since the engine waits to see whether a second press follows; `double_ms: 0` turns double presses off and makes short presses immediate again.

## M6: on a fresh wall the admin password is set before Wi-Fi is joined

Spec: admin password set during first-time setup; the plan listed the flow as join Wi-Fi, then set the password. On the setup hotspot only the card holder can reach the wall, but the moment it joins the home LAN with no admin password, anyone on that LAN could claim it through the open first-run `/api/auth/setup` (the M4 behaviour). So the setup wizard (`/setup`) asks for the admin password as step 1 when none is set, then the network list and password. The API rule the plan asked for is still in place: setup endpoints (`/api/network/setup`, `/api/network/wifi*`) are reachable without login only while the hotspot is up **and** no admin password exists; everything else stays behind login at all times.

Threat model, briefly:
- Hotspot: WPA2-PSK with the per-unit password from the card (`$LEDPOSTER_DATA/setup-password`, generated at install, 10 unambiguous characters, never shown on the wall). Joining it is the trust boundary for first-run setup. It is only up when nobody has set up Wi-Fi yet or someone holding the physical button asked for it.
- While the hotspot is up the captive portal probes redirect to `/setup`; the setup page is static and public like `/login`, the data is not. A wall that already has an admin password requires login even on the hotspot.
- Wi-Fi passwords go to NetworkManager (`nmcli ... password`), which stores them in `/etc/NetworkManager/system-connections` (root only); they are not written to the config or logs. Process arguments are visible to local users while `nmcli` runs; acceptable on a single-user appliance.
- The static IP change and hostname change require login; the rollback only ever moves a connection back to DHCP.
- The `ledwall` user gets five NetworkManager polkit actions (`network-control`, `settings.modify.system`, `wifi.scan`, `wifi.share.protected`, `wifi.share.open`: what `nmcli` needs to scan, join, add/modify/delete profiles and raise the shared-mode hotspot; not `enable-disable-*`, `sleep-wake`, `reload`, `checkpoint-rollback` or `settings.modify.hostname`), the two hostnamed actions, and start/stop of two fixed units: it can change the wall's network, nothing else.
- The DHCP rollback does not depend on the timer surviving a reboot: `ledposter-net-rollback.service` is also enabled at boot with `ConditionPathExists=/data/net-rollback`, so a reboot inside the 120s window reverts the unconfirmed static IP once NetworkManager is up (the app removes the note on confirm).

## M6: how the engine's `show_text` and `wifi_setup_requested` are used

M6 was built in parallel with M5 and verified against `docs/protocol.md` as M5 built it. The networking code only touches the engine through `Engine.show_text(text, seconds)`, `Engine.setup_request(status)` and `Engine.ack_wifi_setup()` in `web/ledposter/engine.py`. `show_text` takes `text` (max 500 bytes, the renderer wraps and honours `\n`) and `seconds` (0.5 to 86400); the wall texts stay well under both. `wifi_setup_requested` is a boolean that stays true until `ack_wifi_setup`: the web app raises the hotspot when it sees it, then acks; if the hotspot cannot come up it still acks (otherwise the flag would re-trigger every poll) and does not retry for 30s. The engine shows its own "Wi-Fi setup" text for 4s on the hold; the web app's hotspot text replaces it a few seconds later.
## M7: `paho-mqtt` 2.x from pip

The stack names paho-mqtt. Bookworm's `python3-paho-mqtt` is 1.6, whose callback API differs; the web app uses the 2.x API (`CallbackAPIVersion.VERSION2`), so `requirements.txt` pins `paho-mqtt>=2,<3`, installed into the venv with pip. Pure Python.

## M7: the HA effect list has the modes that need no choice, plus playlists

Spec: effect list = modes and playlists. Modes that need the user to pick something first (the "Media item" mode needs an item; the generic "Playlist" mode needs a name) are not effects on their own. Each playlist is an effect instead (`Playlist: name`), and modes with settings run at the engine's defaults (Solid colour is white). The list comes from the engine's `list_modes`, through the same mapping as the app's mode picker. A single media item can be played from HA by putting it in a playlist.

## M7: E1.31 multicast and the Linux group limit

Spec: E1.31 receiver for 128 x 192 pixels (145 universes). Unicast works with no setup. With `e131.multicast: true` the engine joins one multicast group per universe, but Linux allows 20 groups per socket by default (`net.ipv4.igmp_max_memberships`); the engine joins what it can and logs how many. The M8 installer raises it to 160 (`/etc/sysctl.d/90-ledposter.conf`, system/etc); without the installer it is left to the user (README).

## M8: `unattended-upgrades` on a read-only root runs in a weekly maintenance window with two reboots

Spec: `unattended-upgrades` for security patches, and a read-only root filesystem (overlayfs). The two conflict: a package upgrade written to the overlay's RAM upper layer is gone at the next reboot, so the stock daily apt timers would download and "install" the same patches every day for nothing. Instead the installer disables `apt-daily.timer`/`apt-daily-upgrade.timer` and `ledposter-maintenance.timer` checks hourly for the window from Settings > Software > Security updates (`maintenance:` in the config, default Sunday 04:00, written to `/data/maintenance.conf`). In the window `ledposter-sys maintenance` writes `/data/state/maintenance-pending`, turns the overlay off (`raspi-config nonint disable_overlayfs`) and reboots; at that boot `ledposter-maintenance-resume.service` runs `apt-get update` and `unattended-upgrade` on the real root while the wall keeps showing, turns the overlay back on and reboots again. Power-cut safe at every point: the marker is written and synced before the cmdline flips, so a cut before the flip leaves the overlay on and the marker is cleared at the next boot; a cut during the upgrade is resumed (apt/dpkg recover) at the next boot; a cut after the overlay is re-enabled but before the marker is cleared is detected by `ledposter-sys boot` (overlay wanted, overlay on: clear). `/data/state/overlay-wanted` records that the overlay is meant to be on, so an installation with `--no-overlay` never gets one turned on behind its back. Logs go to `/data/logs/maintenance.log`.

Kernel and firmware packages (`linux-image-*`, `raspi-firmware`, `rpi-eeprom`) are blacklisted in `/etc/apt/apt.conf.d/52ledposter`: a kernel that changes while the overlay's initramfs/boot files are managed by raspi-config is the one upgrade that can leave the wall unbootable, and the boot partition is mounted read-only (`enable_bootro`). They are a manual step: `sudo ledposter-sys overlay off`, reboot, `sudo mount -o remount,rw /boot/firmware && sudo apt full-upgrade`, `sudo ledposter-sys overlay on`, reboot. Userland security patches (OpenSSL, OpenSSH, Python, ffmpeg, NetworkManager, ...) are covered.

## M8: hotspot DHCP and DNS ports are always open on the Wi-Fi interface

Spec: `ufw` allows only HTTP, mDNS, MQTT outbound and DDP/E1.31 when enabled. The captive portal needs the phone to get an address (DHCP, UDP 67) and to resolve names (DNS, 53) from NetworkManager's dnsmasq while the hotspot is up. Rather than switching the firewall from inside the setup loop (which can run while the web app is being restarted), `ledposter.system.firewall_rules` always allows 67/udp and 53/udp+tcp **inbound on the Wi-Fi interface only** (`wlan0`, or `network.wifi_device`). On the home network nothing listens on those ports (dnsmasq only runs in shared mode), so the exposure is nil; outbound stays default-allow (MQTT), everything else inbound is denied. SSH (22/tcp) is opened only in key-only mode, DDP (4048/udp) and E1.31 (5568/udp) only when `ddp.enabled`. Forwarding is left at ufw's default deny, so a phone on the hotspot cannot use the wall as a router.

## M8: what survives a reboot with the overlay on

Not a spec deviation, but an easy trap. Everything outside `/data` is read-only and the overlay's writes are RAM. So: Wi-Fi profiles (`/etc/NetworkManager/system-connections`) are bind-mounted from `/data/state/nm` (fstab, by the installer) and backed up to `/data/state/nm-backup` at every boot, which puts back a garbled profile (or every profile when none good is left; one deleted while others are fine stays deleted, its backup dropped) before NetworkManager starts; the hostname set in Settings is persisted to `/data/state/hostname` by `ledposter-net hosts` and restored at boot by `ledposter-boot.service` before Avahi starts; ufw rules and the sshd drop-in (key-only, `MaxStartups 20:30:60`, `LoginGraceTime 30`, and on OpenSSH 9.8+ the private ranges exempt from `PerSourcePenalties`; checked with `sshd -t`, a rejected one leaves the previous drop-in in place) are re-applied at every boot by `ledposter-firewall.service` and `ledposter-ssh.service` from `/data/firewall.rules` and `/data/ssh/`; `ssh.service` itself is left disabled and started by that unit only in key-only mode; `fake-hwclock` keeps its stamp on `/data/state`; journald is volatile (system logs vanish at reboot, capped at 32MB RAM; a persistent journal was tried and its card writes did not survive the power pulls) and what must survive is written under `/data/logs` by the app, the updater and the maintenance script. NetworkManager's lease and seen-BSSID state is not persisted; the stable DHCP client id (MAC) makes routers hand back the same address anyway.

## M8: the installer cannot create the data partition on a card that already filled itself

Spec: media, config and logs on a separate writable partition. Raspberry Pi OS grows the root partition to the whole card on first boot (`init_resize.sh`), and a mounted ext4 root cannot be shrunk in place. `install.sh` therefore uses an existing partition labelled `ledpostdata`, or creates one in unallocated space at the end of the card (`sfdisk --append`, `mkfs.ext4 -L ledpostdata`); otherwise it stops and prints the options: remove `init=/usr/lib/raspi-config/init_resize.sh` from `cmdline.txt` before the first boot (README has the step-by-step), shrink from another computer, make the partition by hand, or `--data-dir` for testing (a directory on the root, which forces `--no-overlay`). `/data` is mounted `noatime,commit=15` by PARTUUID with `x-systemd.device-timeout=10` and fsck pass 2.

## M8: system files are not changed by the in-app update

The updater (web/ledposter/updater.py) runs on a read-only root: it fetches, builds and switches the release under `/data/app` and restarts the two services, but it does not install new systemd units, polkit rules or `/usr/local/bin` scripts (deliberately: those are what keeps the web app out of root, so only an admin with a shell changes them). A release that changes anything under `system/` needs `sudo ledposter-sys overlay off`, a reboot, `sudo /data/app/current/system/install.sh` (idempotent; it re-applies the system files and leaves the data alone) and the overlay back on. The README's update section says so, and `git diff --stat <old>..<new> -- system/` shows whether a release needs it.

## M8 review: the `ledwall` user has no path to root

The web app is the network-facing code, so the threat model assumes it can be compromised: everything the `ledwall` user can reach must stay `ledwall`. The final review of m8 found paths out of that box; what is true now:

- **The service accounts are `ledwall` and `ledwall-build`, not a person's login.** Up to m8.5 they were `ledposter` and `ledposter-build`, but `ledposter` is also the natural name for the Pi's login user (uid 1000, in group `sudo`), and when that user already existed the installer reused it: the polkit rules (`subject.user == "ledposter"`), the app's files, the engine's drop target and the `gpio`/`i2c`/`video` groups all went to the admin's own account, and the "no path to root" model below no longer held. The installer now creates the system users `ledwall`/`ledwall-build` (nologin, home `/data/app`), refuses to run if either name exists as a login user (home under `/home` or in group `sudo`), and never chowns, `usermod`s or writes anything of the login user; it only reads that user's `~/.ssh/authorized_keys` for key-only SSH. A wall installed before the rename has its data owned by the old `ledposter` system user and is not migrated: reflash it.

- **`/data/app` is root's.** The engine (`ledposter-engine.service`, root until the matrix is up) runs `/data/app/current/engine/ledengine`; m8 had the whole tree owned by the service user (then called `ledposter`), so a compromised app could replace the binary and restart the engine (polkit allows the restart). Now the installer and the updater own `/data/app` as root, 755: the app reads and runs the current release and cannot change it. `ledposter-update.service` therefore runs as **root**, and its one input, `/data/update-request.json`, is read with `O_NOFOLLOW`, must be a regular file owned by `ledwall` (or root), under 64KB, JSON, with a `target` that matches `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$` **and** is a tag `git ls-remote` reports on the repository; nothing from the file reaches a shell. The clone runs as root with the deploy key (the remote is ours). **make, venv, pip and the tests run as a third system user, `ledwall-build`**, in the release directory, which root chowns to itself afterwards and marks `.ready`. Why a dedicated user rather than root or `ledwall`: `pip install` executes setup code from PyPI and `make` runs the checkout's Makefiles, which should not happen as root; and they must not run as `ledwall` either, because root then executes the result (the engine binary), so a compromised app could have tampered with the compiler's output. `ledwall-build` owns nothing root runs and nothing `ledwall` can write (its home is `/data/app/build`, 700). The deploy key stays readable by group `ledwall` (640) so "Check for updates" (`git ls-remote` inside the app) works; it is read-only on GitHub, so a compromised app can read the source it already runs, not more. `known_hosts` is seeded by the installer (`ssh-keyscan github.com`).
- **`/data` is `root:ledwall` 1775** (sticky), not `ledwall`-owned: the app can create and atomically replace its own files at the top (config.yaml, secret, the unit inputs) but cannot rename or remove `app/`, `state/` or `logs/`, which are root's; so root-side code can use those paths without a `ledwall` process swapping a symlink in. The app's own directories (`media/`, `ssh/`, `logs/web/`) are created by root with `mkdir`+`chown` in one go and never chowned again; the web log moved to `logs/web/web.log`. Layout table in docs/ARCHITECTURE.md.
- **Root never sources or follows the app's files.** `ledposter-sys maintenance` used to `. /data/maintenance.conf` as root; it now parses it: every line must match `^(ENABLED|DAY|HOUR)=[0-9]+$`, `ENABLED` 0/1, `DAY` 0-6, `HOUR` 0-23, else the file is refused and the defaults apply. Every input (`firewall.rules`, `ssh/mode`, `ssh/authorized_keys`, `maintenance.conf`, `net-rollback`, the update request) goes through `ledposter-sys input` (Python: `openat` with `O_NOFOLLOW` on every path component, regular file, owner `ledwall` or root, 64KB cap, no NUL) and then line by line through the same regexes the app uses; `authorized_keys` is no longer copied with `install` (which follows symlinks) but written from the validated lines. Hostname files and `/etc/hosts` are only ever written from root-owned `state/`; the factory reset's `rm -rf` of the app's top-level entries relies on coreutils `rm` not following symlinks, and the directories it recreates are made and chowned in one step.
- **"Run maintenance now" works**: the request moved from root-owned `state/` to `/data/maintenance-request`, next to the other unit inputs.
- **The engine takes nothing security-relevant from the config while root** (closed in the commit after m8; m8 itself still had the gap described next). The engine reads `/data/config.yaml` (the app's file) as root before it drops privileges, and up to m8 it took `engine.socket`/`engine.preview_socket` (unlinked, bound and `chown`ed by path as root: an arbitrary unlink/chown with a TOCTOU window) and `engine.user`/`engine.group` (so `root` would have meant no drop at all) from it: a `ledwall`-to-root path. Now, as root, those four come only from the command line (`--socket`, `--preview-socket`, `--user`, `--group`, set in the root-owned `ledposter-engine.service`) or the built-in defaults (`/run/ledposter/{engine,frames}.sock`, `daemon:daemon`, for `sudo ./ledengine` by hand); config keys that differ are logged once and ignored. The config keys still work when the engine is not root (dev, `make sim`), and `engine.socket`/`preview_socket` stay in the config as the paths the web app connects to; the installer no longer writes `engine.user`/`group`. Even with the flags, as root: the drop target may not be `root`, uid 0 or gid 0, and a name that does not resolve is fatal; both sockets must be plain names (absolute, no `.`/`..`/empty parts) in one directory, which the engine creates (`mkdir` 0770, `fchown` to root:group on the fd it opened) or verifies (`O_DIRECTORY|O_NOFOLLOW`: a real directory, owned by root, not world-writable, like the unit's `RuntimeDirectory`); only an existing *socket* (`lstat`, `S_ISSOCK`) is ever unlinked before binding, a regular file or symlink at the path is refused and left alone; the socket's mode 660 comes from the umask and its group from the effective gid while binding (`fchmod`/`fchown` do not reach a bound socket's path on Linux, and nothing is chowned or chmoded by path any more); and if the engine is still root after the matrix library started (the library only logs a failed drop), it exits. Checked the other root-time reads of the config: `fonts.dir` (BDF files, `fopen` read-only), `button.chip` (`open(O_RDONLY)`), `sensors.bh1750.i2c_bus` (an integer, `/dev/i2c-N` `O_RDWR`: the `ledwall` user is in `i2c` anyway), media (`open(O_RDONLY)`); nothing is written, created, chowned or unlinked from a config value while root. Unit tests: `engine/tests/test_engine.cpp` (`test_privs`). Residual: a member of group `ledwall` has write access to `/run/ledposter` and can still delete or squat the socket names (a denial of service it already had), and the stale-socket probe `connect()`s by path to a name that `lstat` said was a socket a moment earlier (a connect-and-close as root, no data).
- **Still as before, worth knowing:** `ledwall` may restart the engine and the web app (what they execute is root's now), start the fixed units, reboot through logind, and change the network.

## M8 review: `/data` mounts with `nofail`

A card whose data partition is damaged or missing used to stop the boot in systemd's emergency mode (no network, no SSH). Both fstab lines (`/data` and the `state/nm` bind mount) now carry `nofail`, so the boot continues. The engine, web, update, boot and maintenance units keep `RequiresMountsFor=/data` and simply fail (there is nothing to run without `/data`: the software lives there). `ledposter-firewall.service` and `ledposter-ssh.service` are ordered after `data.mount` but no longer require it: with `/data` absent (no `/data/state`), `ledposter-sys firewall` leaves ufw's install-time rules alone and `ledposter-sys ssh` keeps the key-only setup the installer (or the last maintenance boot, when the root was writable) left in `/etc/ssh`, so a wall installed with `--ssh-key` stays reachable to repair the partition (README: Troubleshooting). A wall installed with `--ssh disabled` is not reachable in that state; that is the trade-off the owner chose.

## M8 review: the limiter ceiling is capped at 15A

The spec's supply is 100W PD, about 15A at 5V for the panels. The settings API accepted up to 100A; it now refuses anything above `config.MAX_CEILING_AMPS` (15), `config.load()` clamps a hand-edited file to it with a warning, and the engine clamps and logs the same (`power.ceiling_amps ... clamped to 15A`), so no layer can be talked into a ceiling the supply cannot deliver.

## M8: the engine starts on a boot screen, not the panel-ID pattern, and the web app restores the last mode

M1 to M7: `ledengine` without flags showed `panel-id`. Spec: "engine starts first and shows the boot screen". So without a mode flag the engine now shows `boot` (`LED POSTER` + spinner, protocol.md), and the web app persists every `set_mode` it makes in the config (`last_mode`) and sends it once per engine start when the engine reports `mode: boot` (`ledposter.system.LastMode`). A `media` last mode whose item is gone stays on the boot screen. `--pattern panel-id` still works for bring-up, and Settings > Panel ID test is unchanged.

## M8: config file mode is 640, not 600

M4 wrote `config.yaml` mode 600. The engine drops root to the `ledwall` user and must read the config for `reload_config`, and the web app runs as the same user, so 600 would also have worked; 640 (group `ledwall`) is used so a future split of the two processes into different users of one group needs no change, and because the data dir is owned `ledwall:ledwall` 750 anyway. The secrets inside (password hash, token hashes) stay within the group; `$LEDPOSTER_DATA/secret` (the session signing key) stays 600.

## M8: the update's self-test is the engine's `make test` plus an import check

Running the web app's full pytest on the Pi takes a few minutes of ffmpeg work, so an update runs `make -C engine test` and `python -c "import ledposter.app"` in the new release before switching; the real acceptance is the health check after the switch (`/api/health` reports the new release and the engine answering within 90s, else automatic rollback).

## M8 hardening: releases are built off the Pi

The spec has the wall install and update from its own checkout. On the real wall (Pi 3B, 1GB, powered from a USB port and permanently under-voltage) a build on the device ran out of memory with the engine and the web app running, locked the Pi, and the updater resumed it at every boot until the card was lost. So the recommended path builds nowhere near the Pi: `tools/build-release.sh` builds the release in a `debian:trixie` linux/arm64 container with the installer's own package list (`system/packages.sh`, sourced by both), at the release's final path `/data/app/releases/<version>` (a venv and the engine's compiled-in fonts dir are absolute paths), runs `make test`, byte-compiles (the web app cannot write `__pycache__` into the root-owned release), and writes `ledposter-<version>-arm64.tar.zst` plus `.sha256`; `<version>` is `git describe --tags --always`, the installer's release name. `install.sh --prebuilt TARBALL` checks the sha256 when the file is next to it, insists that the tarball's version is the checkout's (system files come from the checkout), unpacks it as root, checks the venv's Python version, the engine's libraries and the venv's imports, and leaves the release exactly as a build does (`root:root`, `.ready`); it installs only the runtime packages, so a prebuilt wall has no compiler. `tools/deploy.sh` does all of it over SSH. The tarball is tied to Debian trixie (Python 3.13, `libyaml-cpp0.8`). Building on the Pi stays as the fallback, now with one make job, no pip cache and at idle priority.

## M8 hardening: an interrupted update build is never resumed

`ledposter-update.service` still runs at every boot, because a power cut during a switch must be finished or rolled back (`pending.json`). But when the saved state is fetching, building or testing, `updater.py run` no longer resumes: it deletes the half-built release (never `current`, `previous` or a release with `.ready`), removes the request that started it, sets the state to failed with "Update to X was interrupted (power loss or reboot); still running Y. Start it again from Settings." and exits 0. The web app refuses a new request while an update is active, so a request file found with such a state is always the stale one. A build on the device runs with `MAKEFLAGS=-j1`, `pip --no-cache-dir`, `Nice=19`, `IOSchedulingClass=idle`, `CPUWeight=10`, and does not start unless MemAvailable + SwapFree is at least 400MB (`updater.MIN_BUILD_MEMORY_MB`); on a wall without a compiler (installed with `--prebuilt`) it refuses before fetching anything and points to `tools/deploy.sh`.

## M8 hardening: the in-app updater does not download prebuilt releases

Not done: having "Update to X" fetch `ledposter-<tag>-arm64.tar.zst` from the GitHub release instead of building. The repository is private, and release assets of a private repository are only reachable through the GitHub API with a token; the wall's credential is a read-only deploy key, which works for git over SSH but not for the API. Doing it properly needs a token with read access on the wall (the threat model counts the deploy key as the only secret a compromised app can read) or a public place for the tarballs. Until then the in-app update builds on the device (with the limits above), and a wall installed with `--prebuilt` is updated from a computer with `tools/deploy.sh --tag <tag>`.
